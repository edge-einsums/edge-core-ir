## Bugs (found — EDGE-ZOO verification round)

Surfaced when the EDGE agents (expert + auditor + validator) reviewed the BFS and Bellman-Ford artifacts before publishing them to the EDGE-ZOO.

- [x] **Bellman-Ford UPDATE encodes `<<` as `take_right(union)`, which is not `<<`.** — fixed. `<<` now ships as the default compute op `update` in the UDF registry (`edge_ir/udf/builtins.py`), paired with the union merge; the builder uses it. Verified end-to-end through the new reference evaluator: 29/29 graphs against an independent textbook relaxation. Original text follows.
 Step (4) `D_{i+1,d} = D_{i,d} · NewlyRelaxed_{i,d} :: ⋀_d <<(∪)` is built in `examples/algorithms/bellman-ford/build_bellman_ford_program.py` as UDF compute `take_right` + `union` merge. `<<` carries the *left* operand forward where the right is empty; `take_right(union)` returns the right operand's empty value there and drops it. They diverge on the (left present, right absent) case — "distance unchanged this round," i.e. most vertices most rounds — so under faithful semantics the cascade converges to `D = {}` rather than the correct distances (confirmed by simulation). RECORD's `take_right(intersect)` is fine; only UPDATE is wrong. Fix (decided): ship `<<` as a **default compute op in the UDF registry** — the update operator = right operand where present, else carry the left forward — paired with the union merge. The paper defines `<<` as a compute op, NOT a merge (`tex/appendix/1-misc.tex:76-81`). See Bigger systems → User-defined function registry.

- [x] **DFS has the same `<<` gap (its G3).** Same root cause as the BF UPDATE bug; fixed together — done.

- [ ] **Bellman-Ford metadata mislabels the `<<` gap.** `examples/algorithms/bellman-ford/metadata.md` calls G1 "faithful-for-this-input" and asks whether `<<` should be a "17th merge symbol" — both wrong (it is not faithful, and `<<` is a compute op, not a merge). The `<<` definition is cited as `tex/appendix/2-bf.tex:62-113`; the definition actually lives at `tex/appendix/1-misc.tex:76-81` (2-bf only *uses* it).

- [ ] **BFS metadata claims `decl-G` is "exact" against the paper when it corrects it.** `examples/algorithms/bfs/metadata.md` marks `decl-G` "exact" vs `seqn:Gf`, but the artifact (correctly) drops the spurious `I` rank that `seqn:Gf` carried on the static graph. Reword to note the intentional correction. Also the "Variant" line cites `eqn:bfsi` (uses `min`); the artifact uses `ANY`, so cite `eqn:bfsior` / `eqn:edge_bfs_full`.

- [x] **Paper `seqn:Gf` carried a stray `I` rank on the static graph `G`.** `tex/bfs-example/07-iteration.tex:152` declared `G^{I,S,D}`, but `G` is static and the paper's own rule (`:51`) says only per-iteration tensors carry `I` (`F`, `T`, `P` correctly do). Changed to `G^{S,D}`. — done

- [x] **DFS STAMP and `S_0` use a constant `Stamp` placeholder instead of a per-point rank-as-value.** — fixed by adding the `RankValue` leaf to the `Expression` union (see Language features below). Both strict xfails now pass. Original text follows.
 `examples/algorithms/dfs/build_dfs_program.py` encodes STAMP's RHS (and the `S_0` init RHS) with the zero-rank `Stamp` constant, but the einsum wants the per-iteration-point stamp σ(i+1,v) (and σ(0,v)=v for init) — a value that depends on the iteration coordinates. There is no IR leaf for a "rank-as-value" operand yet. Surfaced by the new DFS tests (DFS gap G1; 2 strict xfails).

- [ ] **Max-flow: pin the empty values (the einsum under-specifies them as bare "empty").** `examples/algorithms/max-flow/einsum.md` declares G, C, F, R, E, D as `→ Integer, empty` with NO value; the builder fills `0` for all. For capacity (G, C), flow (F), residual (R), and excess (E) that is correct — a missing capacity/flow/residual/excess genuinely *is* 0, and a present-0 behaves identically to absent wherever those are read (sums, `>0`, etc.). The one tensor where 0-vs-absent changes behavior is **height `D`**, and it's the INTERSECT reads of `D` that cause it, NOT a union merge: the height rule (E09, `D_{i,v} +(∩) 1`) and the relabel's neighbour-height gather (E22, `... →(∩) D_{i,v}`) both read `D(v)` through intersect, so a height-0 neighbour declared `empty=0` is absent → dropped *before* it can reach the `min(∪)` in E23. Under a union/pass-through read the empty 0 would be substituted and seen by the compute, and there'd be no issue. Also the einsum explicitly inits `D_{0,u}=0` for all u, which is a no-op under `empty=0` — a strong sign `D` wants a non-zero empty sentinel (or those reads want a different merge). UNCONFIRMED (no evaluator; max-flow einsum itself still unverified). The earlier "all six empty=0 is a bug" framing was too broad — the `test_max_flow_integer_tensors_empty_is_the_empty_sentinel` xfails over-assert and should be narrowed to `D` once its intended empty is settled during max-flow verification. `metadata.md` marking these `decl-*` rows "exact" is still wrong (the einsum gives no value). (Also: max-flow has no `*_program.json` on disk — only the builder.)

- [ ] **Max-flow is not single assignment.** A cascade is single assignment: two Einsums may not write the same tensor slice. `edge_ir/validator/single_assignment.py` reports 12 violations in max-flow, on `D`, `F`, `E`, `R` and `Act`. bfs, bellman-ford, dfs and label-propagation report none. One violation already produced wrong behavior: E17 wrote `Adm_{i+1}` and the next round's push step wrote that same slice, and since the evaluator does not clear a slice before a second write, stale admissible edges survived and vertices pushed along edges that the height rule no longer admitted. E17 now writes `AdmPost`, and `einsum.md` still shows `Adm`, so the spec and the builder disagree until Sanjana and I settle it. The rest stand in for IR features that do not exist yet. The preflow initializes generation 1 from inside the cascade, so it reruns every round (`F`, `E`, `R`). E04's case statement is lowered to three writes of the same slice of `R`, which relies on later-overwrites-earlier. Both `D[1,u]` writes in the initialization section land on one slice for the same reason. The relabel step recomputes `Act_{i+1}`, which the next round's push step writes again; the two agree today, so nothing breaks. Fix: move initialization out of the cascade or write generation 0, give the relabel step its own tensor, and encode E04 once the IR has a case statement (see Language features). Then the pass reports nothing and `tests/test_validator_single_assignment.py` asserts that.

- [x] **Added einsum-derived artifact tests for bellman-ford, dfs, max-flow; strengthened bfs.** Every assertion derives from each `einsum.md`, not from the JSON, so they catch encoding divergences instead of blessing them; known-buggy encodings are `strict` xfails that flip to a hard failure the moment they're fixed. Results: bellman-ford 20 pass / 1 xfail (the `<<` bug); dfs 34 pass / 3 xfail (`<<` + 2 rank-as-value); max-flow 48 pass / 6 xfail (the empty-value bug); bfs 16 pass (added einsum (b)/(c) coverage, no bugs). — done

- [x] **Rank variables as tensors (rank-as-value operands).** — done. `RankValue(kind="rank_value", expr: RankExpression)` added to the `Expression` union in `edge_ir/ir/expr.py`, and `edge_ir/analysis/iteration_space.py` walks it (a rank value's variables are axes). This also covers a shape symbol in value position (`|V|`, `|R|`), since `RankConstantShapeSym` is already a `RankExpression`. Original text follows.
 The IR `Expression` union (`edge_ir/ir/expr.py`) has no leaf for a rank variable used as a *value* in operand position; rank vars only show up as subscripts (`RankExpression`). The paper allows this ("Rank Variables as Tensors", `tex/bfs-example/09-rves.tex:101-111`). It is needed for the DFS order-stamp `Stamp_{i,v} = (i × |V|) + v` (read as `Stamp_{i+1,v}`) and the post-order finish-time term `F_{i,v} · i`. Add a `RankExpressionValue`-style leaf so these are expressible. This is the general feature behind the DFS rank-as-value bug in the Bugs section (the per-point `Stamp` placeholder).

## Bigger systems

- [ ] **Split the interpreter out of the core IR.** Decided to publish one repository first and split afterwards, because the examples only run because the evaluator ships with them, and the split needs work that the first public release does not. The line is almost clean already: `edge_ir/evaluator/` imports `ir`, `udf`, `analysis` and `runtime`, and nothing imports it back except `edge_ir/udf/registry.py` and `edge_ir/udf/builtins.py`, which reach into the evaluator for `PopulateAction`, `PopulateContext` and `is_empty_value`. Order of work: move those three into a shared module, split `udf` along the decl/impl line it already documents (the validator wants declarations, the evaluator wants implementations), then cut the two repositories and have the interpreter depend on the core package.

- [~] **User-defined function registry.** — first cut landed in `edge_ir/udf/` (`FunctionRegistry`, `UdfDecl`/`UdfImpl` decl-vs-impl split, `default_registry`). Ships `<<` as `update`, `𝟙` as `identity`, the relational operators under both short and spelled-out names, and the `select-{min,max}-{val,coord}` coordinate operators. Adding a function requires no evaluator change — pinned by `tests/test_evaluator_extension.py`. Not yet built: the directory loader and decorators of §3/§7.2. Original text follows.
 The IR only stores function names (`min`, `OR`, `take_left`); the actual implementations are registered separately at execution time. This covers all six function categories: compute (arithmetic like `+`), merge (existence-deciding ops like `∩`), coordinate (used inside populate, picks where to write), unary (negation, NOT), rank-mapping (iteration-point → coordinate functions like `min(a,w)`), and boolean (used in `DiamondBooleanApp` stopping conditions). Design sketch in `docs/udf_registry_plan.md`.

  **Default compute ops the registry must ship with include `<<`** — the update operator: right operand where present, else carry the left forward, paired with the union merge. This is the fix for the BF/DFS `<<` bug in the Bugs section (currently mis-encoded as the builtin `take_right`, which returns the right's empty and drops the left value instead of carrying it forward).

- [~] **Layer 2 validator.** First pass landed: `edge_ir/validator/single_assignment.py` checks that no two Einsums write the same tensor slice, across the initialization section and the cascade, and accounts for the iterative rank (a write to `X_{i+1}` in round `i` hits the slice that round `i+1` writes as `X_i`). It returns a list and does not raise, so a program that violates the rule still loads and runs. Enforcing the rule in the IR itself waits until max-flow is single assignment (see Bugs). Original text follows.
 The IR (Layer 1) only checks structure — Pydantic verifies each node's shape. The Layer 2 validator runs after Pydantic, before execution, and does the cross-reference checks (every tensor name actually resolves to a declared tensor, every UDF is registered, every binary label has matching specs, etc.) plus type checks (`empty_value` matches the declared data type, operators used in the right slots). Errors come back as a list, not one-at-a-time, so a UI can surface every problem in one pass. Sketch in `edge_ir/validator/README.md` and `docs/interpreter_future_plan.md`.

  **Predicate-specific checks (from the restricted-iteration-predicates round):**
  - Every rank variable referenced inside a predicate must already appear somewhere in the surrounding Einsum (in the output rank list, in some input projection, or both). The predicate cannot introduce a new rank variable.
  - In `SetMembership(rank_variable, coord_set, negated)`, when `coord_set` is the new `CoordSetName(name)` variant, `name` must resolve to a coordinate set the host runtime knows about. Same shape as the tensor-name resolution check — the IR carries the name; the validator checks against the runtime registry.
  - When `coord_set` is `CoordSetInterval(lo, hi)` (the range case), shape-symbol endpoints (`"|V|"`, `"N"`) must resolve, and `lo ≤ hi` must hold (after resolution). When it's `CoordSetEnum(coords)`, the coords must be type-compatible with the rank variable's coordinate space.
  - In `PredicateComparison(lhs, op, rhs)`, both sides must be coordinate-valued expressions (rank var / rank constant / shape symbol / rank arith / rank function). A tensor-projection-valued thing on either side is rejected — predicates restrict iteration, they don't read tensor values to do it.
  - For composition: `LogicalAnd`/`LogicalOr` need ≥ 2 operands (Pydantic enforces). `LogicalNot` wraps one. Nested composition is fine; the validator may want to flag double-negations or trivially-false compositions (`pred ∧ ¬pred`) as suspicious, but doesn't have to reject them.

- [ ] **Semantic layer / shared analysis.** To actually run a program you need to compute things from the IR — what's the iteration space, which ranks does this reduce collapse, is this expression affine. These calculations don't depend on which backend you're using (the paper pins them down), so they live in `edge_ir/analysis/` and every consumer calls the shared functions. The validator and the evaluator will be the first two callers. The existing `edge_ir/analysis/affine.py` is the prototype shape: a pure function, returns a dict keyed by node, lives outside the IR.

- [ ] **AST and parser.** Right now you build the IR by hand in Python (see `scripts/build_bfs_program.py`). The plan: text → Lark parser → AST (the parser's tree, sugar preserved, source spans on every node) → lowering → IR. The AST module lives at `edge_ir/ast/` (currently empty). Translation from the paper's Unicode glyphs (`∧`, `∨`, `≡`) to ASCII happens at the parser, before the IR sees anything. Plan in `docs/interpreter_future_plan.md`.

- [~] **Reference interpreter + debugging tooling.** — first cut landed in `edge_ir/evaluator/`, built directly on the core IR. Module layout mirrors the EDGE semantics (spaces / tensors / projection / iteration / actions{map,reduce,populate} / einsum / cascade / stopping / order). Randomized iteration-order mode is implemented (`ShuffledSchedule` + `check_order_independence`). UDF registry in `edge_ir/udf/`. Verified: BFS 38/38 and Bellman-Ford 29/29 against independent references, DFS pre-order 40/40 on trees. Still open: nested cascades, post-loop section, case statements, macros/rank groups. Original text follows.
 The thing that actually runs an EDGE program: build the iteration space, walk each point, evaluate input projections, apply the map/reduce/populate semantics from the paper, run the cascade, check stopping conditions after each iteration, advance generational ranks. Plus debugging tools. One planned feature: a "randomized iteration order" mode that visits points in a shuffled order — if the result changes between runs, the program (or the interpreter) was secretly relying on iteration order, which violates EDGE's semantics. Sketch in `docs/interpreter_future_plan.md`.

## Done

- [x] **`RankFunction.args` now accepts any kind of rank expression.** Variables, constants, structured arithmetic like `m+1`, even nested function calls. So `min(a, 0)`, `f(m, |V|)`, and `f(g(x))` are all legal as arguments now. Before, args could only be bare rank variables. Recorded as D12 in `design_decisions.md`.

- [x] **`TensorDeclaration.empty_value` is required but can be `None` / JSON null.** Every tensor has to declare an empty value — you can't omit `empty=` — but writing `empty=null` is a valid choice (works for any datatype, since JSON `null` ↔ Python `None` round-trips natively). D13.

- [x] **Map/Reduce `rank_list` stays optional.** We tried removing it (the reduce set is usually derivable from the iteration spec — input ranks minus output ranks), but opaque user-defined functions like `f(a,w)` can map iteration points to output coordinates in ways the IR can't derive structurally, so the explicit list has to stay for those cases. For ordinary reduces the validator can cross-check the user's list against the derived set and flag mismatches. D10.

- [x] **`PopulateSpec.rank_list` can be empty now (`min_length=0`).** An empty list means "no mutable rank" — that's the default-assignment populate, which is the most common case (every BFS einsum uses it implicitly). The field is still required to be present, just allowed to be empty. D11.

- [x] **Settled the IR layering.** The core IR is the stable contract and stays as the desugared form. Each backend (interpreter, future MLIR backend, TeAAL, etc.) builds its own runtime data structures. But the logic that derives facts from the IR (iteration space, reduce set, affineness) is shared — lives in `edge_ir/analysis/` so two backends can't disagree on what the same program means. D14.

- [x] **Analysis results live in side tables, not on the IR.** Anything *computed* from the IR (like "is this RankArith affine?") doesn't get stored on the IR nodes themselves — it goes in a separate dictionary keyed by node identity. Specifically: removed the `is_affine` field from `RankArith` and moved the affine analysis into `edge_ir/analysis/affine.py` (the `analyze_affinity(node) -> Affinity` function). The `is_affine` field on `RankFunction` stayed because that one is user-declared input, not derived. D15.

- [x] **Wrote down that the AST is a separate thing from the core IR.** The parser produces an AST (sugar preserved, source spans attached); lowering then transforms the AST into the core IR (canonical, desugared). They're two separate Pydantic hierarchies, not one. Four reasons to keep them apart: (1) errors can point at what the user actually wrote, (2) future IDE/LSP tooling needs the AST, (3) source-preserving formatters need the AST, (4) you can add new surface syntax without backends having to know. Captured in D3's note.

- [x] **Source locations live on the AST only, not on the IR.** Every AST node carries a "span" saying which file/line/column it came from. When lowering converts AST → IR, it produces a side dictionary mapping each IR node back to its source span (used by validator/interpreter for error messages). The IR itself stays clean of debug info. D16.

- [x] **Lowering errors are collectable, not fatal.** When the AST → IR pass hits a problem, it doesn't stop at the first error — it collects all the errors and returns them as a list, same shape as the Layer 2 validator's errors. So an IDE can show every problem at once instead of a fix-rerun-find-next-error cycle. D17.

- [x] **Hard rule for what the AST is allowed to do.** The AST holds only what the parser actually saw — no inferred fields, no filled-in defaults, no semantic checks. And the AST module doesn't import from the IR module (one-way: lowering imports both). Stops the AST from slowly absorbing IR-like logic and quietly collapsing the AST/IR separation. D18.

- [x] **AST JSON dumps exclude source spans by default.** When the AST gets saved to a JSON file, the source-location spans are left out — they stay in memory for error messages while the program runs, but don't bloat the saved file. Also makes equality work sensibly (the same code parsed from two different files would have different spans but should otherwise compare equal). D19.

- [x] **Split `RankConstant` into two separate node types.** `RankConstantLiteral` carries an actual value (an integer like `3`, or a label like `'a'` from a char-typed coordinate set). `RankConstantShapeSym` carries a name that references a declared shape symbol like `|V|`, `N`, `M` (gets resolved to an integer at iteration-space construction time). Before the split, both cases lived in `RankConstant.value: int | str` and a string value could mean either — you couldn't tell which without context. D20.

- [x] **Scalar literals** — `TensorDeclaration.value` added; `ScalarValue` removed from `stopping.py`; `REGEX_TENSOR_NAME` relaxed to admit `Lit_*` synthesized names; BFS builder reconciled with `einsum.md`; reserved-keyword catalog at `docs/keywords.md` (D21)

- [x] **Restricted-iteration predicates** — `Einsum.predicates` slot; new `edge_ir/ir/predicate.py` module with `SetMembership`, `PredicateComparison`, `LogicalAnd`/`Or`/`Not`; `CoordinateSet` gained `CoordSetName(name)` for host-supplied sets; BFS init block (`F_0`, `P_0`) now fully encoded with `Lit_True` synthesized literal + `SetMembership(coord_set=CoordSetName("id"))` predicates; Layer 2 validation plan at `docs/validator_plan_predicates.md` (D22 explains why predicates and stopping conditions stay as separate IR unions; D23 captures the round)
